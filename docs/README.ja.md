## 概要

Research Team Mode は、単一のチャットではなくチームとしてエンドツーエンドの研究を進めるための DSH エージェントプリセットです。Lead が作業を計画し、2 つの台帳（ユーザーゲート用のボードカード、内部ステップ用のチームタスク）を維持し、作業を割り当て、結果を統合し、ユーザーと対話します。8 名の既定スペシャリストが、顧問レビュー、文献と証拠、データ取得、実験設計、コード、実行、独立レビュー、論文執筆を担当します。

このモードは、数日から数週間にわたる研究、追跡可能な証拠を必要とする研究、明確な役割の境界が有効な研究のために作られています。単発の Q&A モードではありません。Lead は、タスクが実際に必要とする役割だけを作成します。

## 一目でわかる概要

| | |
| --- | --- |
| **既定の役割** | 8: advisor, designer, researcher, data, builder, runner, reviewer, writer |
| **ワークフロー** | ゲート方式：内部ステップは `team_task_*`、ユーザーゲートはボード。作成、claim、実行、報告、レビュー、ユーザーによる受け入れ |
| **完了** | `in_review` がエージェントの最終地点。カードを `done` に移動できるのはユーザーだけ |
| **モデルルーティング** | Plugins ページの設定フォームから、役割ごとに provider、model、reasoning effort を指定 |
| **Git** | 実質的な作業の開始時にエージェントが初期化。破壊的な変更はブランチで行い、受け入れ後にのみマージ |
| **Worklog** | `worklog/PLAN.md` + `INDEX.md` + ゲート対象カードごとに 1 つの有界ファイル。再開時は PLAN と INDEX を先に読む |
| **ランタイム** | PTC（`run_code` + 生成 SDK）。メンバーごとにサブエージェント 1 層 |

## 対象となるユーザー

- 文献レビュー、実装、実験、論文執筆を組み合わせた研究プロジェクト。
- 主張から出典、実行記録、ログまでの証拠の連鎖を必要とするチーム。
- 汎用エージェント 1 つではなく、顧問と独立したレビュアーを求めるユーザー。
- 最終的な受け入れ判断をエージェントではなくユーザーが下すべき作業。

**対象外:** 簡単な事実確認の質問、単一ファイルの編集、単発の回答で足りるタスク。このモードは Lead に対し、単純な質問には直接回答し、実質的な研究にのみチームを動員するよう指示します。

## Lead はあなたとどう話すか

Lead の返答は科学的なコミュニケーションであり、ステータス配信ではない。まず主張または結果を示し、その根拠（run id、データセット、不確実性とサンプルサイズを含む指標、出典）を続け、次に何が不確かなのか、最後にあなたが決めるべきことを述べる。各文は、観測された事実・推論・仮説・未解決の問いのいずれかとして明示され、方法はあなたが追跡し学び続けられる程度に説明される。

内部の仕組みは内部に留める。エージェント間の引き継ぎ、再試行、ツールのエラー、ボードの記帳、チームが作業中に得た知見は、結果の読み方を変える場合や意思決定を妨げる場合を除いて転送されない。メンバーの報告はそのまま貼るのではなく、主張・根拠・限界に翻訳される。

分業は明示されている。あなたが科学的方向を定め証拠を判断し、チームが検索・実装・実験・検証の負荷を担う。

あなたの問いがこのターンの契約です。サーベイ、拡張案のリスト、判断を求められたら、回答はまずそれを届けます。研究計画やゲート、中止基準は追加であって代替ではありません。回答はあなたの問いを順に取り上げ、それぞれに根拠と詳細が載ったファイルを示し、まだ答えられないものは正直にそう言います。

長いターンは沈黙のターンではありません。チームが約十分以上動き続けたら、Lead は短い中間回答を送ります。何が確定し、何を集めていて、次の回答がいつ来るのかを示し、計算資源を使い切る前にあなたが方向を変えられるようにします。

先行研究の否定的結果が縛るのは、それを生んだ手法・データ・予算であり、アイデアそのものではありません。方向を閉じる前に、その最強の版を書き、それでも失敗することを示します。「主張できない」と書くときは必ず、主張できる版と、それを裏づけるのに必要な証拠を添えます。

## 要件

Research Team Mode は**プロファイルレベルの DSH バンドル**です。このバンドルは、自身が利用するプロファイルバンドルをインストールも有効化もしません。DSH のパッケージインストーラーが扱うのは npm 依存関係であり、機能バンドルではありません。まず同じプロファイルで依存関係を有効化してください。

| 機能 | Provider | 備考 |
| --- | --- | --- |
| DSH | [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) `0.2.x` | `0.2.1-rc.5` を基準に開発。他のリリースでも動作する可能性はありますが保証はありません |
| Agent Teams | [`@deepseek-ai/dsh-experimental-agent-team-profile`](https://github.com/deepseek-ai/deepseek-harness) | `spawn_teammate`、`send_message`、`wait_agent`、`interrupt_agent`、`team_task_*`、および Team サービスを提供 |
| PTC ランタイム | [`@deepseek-ai/dsh-agent-tool-presentation`](https://github.com/deepseek-ai/deepseek-harness) と [`@deepseek-ai/dsh-ptc-runtime-node`](https://github.com/deepseek-ai/deepseek-harness) | DSH ベースの一部。`run_code` を有効化 |

**任意の連携プラグイン。** これらは他者が開発したプラグインです。本プリセットはこれらに依存せず、インストールもしません。チームと連携させたい場合にのみ追加します:

- **タスクボード**（[`dsh-taskboard`](https://github.com/cloader/dsh-taskboard)）——`taskboard_*`、ユーザー向けカード、受け入れチェックリスト、`presetId=research-team` の実行セッションを提供します。無い場合、worklog（`PLAN.md`、`INDEX.md`、カードごとのファイル）が永続的な記録になります。
- **Zotero**（`dsh-zotero`）——共有ライブラリのツール（`zotero_*`）と paper-fetch の取り込み経路を提供します。無い場合、文献作業は Semantic Scholar、arXiv、Web を使い、証拠表は主張・出典・位置を記録し続けます。
- **Mnemon**（`dsh-mnemon`）——セッションをまたぐ永続ノート（`mnemon_*`）を提供します。無い場合、worklog と `CHANGELOG.md` が継続性を担います。

依存関係が欠けていてもモードは部分的に読み込まれますが、チームツール、ボード、設定ページのいずれかが利用できなくなります。プラグインマネージャーはこれらのバンドルを促したり、自動でリンクしたりすることはありません。

## インストール

このプリセットは DSH バンドルとして配布され、npm で `dsh-research-team-preset` として公開されています。

### DSH のプラグインページからインストール

1. **必須バンドルを有効化**します: 対象プロファイルで Agent Teams [`@deepseek-ai/dsh-experimental-agent-team-profile`](https://github.com/deepseek-ai/deepseek-harness)。上記の任意の連携プラグインは今からでも後からでも追加できます。
2. **設定 → プラグイン** を開き、**追加** をクリックします。
3. インストール元を貼り付けます: npm パッケージは `dsh-research-team-preset@0.1.1`、ソースを固定する場合は `github:ZhanRuiXin/dsh-research-team-preset#v0.1.1`、ローカルチェックアウトは `link:/absolute/path/to/dsh-research-team-preset`。
4. **DSH を再起動します。** プリセット行とバンドルのクライアント側は起動時に読み込まれます。
5. **同じプロファイルでバンドルが有効になっていることを確認**し、**新しいセッションを開いて** モード選択で **Research Team Mode** を選びます。

### コマンドラインからインストール

```text
dsh plugin add dsh-research-team-preset@0.1.1
```

レジストリではなくソースを固定する場合:

```text
dsh plugin add github:ZhanRuiXin/dsh-research-team-preset#v0.1.1
```

タスクボードの実行セッションでは `presetId=research-team` を付けたカードを作成し、同じ persona とツールで実行します。

> このモードはプロファイル単位のバンドルです。あるプロファイルにインストールしても別のプロファイルでは有効になりません。プロファイルごとにインストールと前提条件を繰り返してください。

## 初回実行

実際の作業を始める前に、Lead に環境とボードの確認を依頼してください:

```text
list_agents        # create only the roles the task needs
research_project   # resolve the current project/workspaceId
taskboard_list     # check existing cards in this project
```

典型的な最初のタスク:

```text
User: "Survey the literature on X, implement the baseline, and draft the method section."
Lead: research_project -> taskboard_create only at user gates -> team_task_create -> send_message
Members: team_task_update (claim) -> work -> complete + send_message; gated steps also claim the card
Reviewer: independent PASS/FAIL with evidence
Lead: summarize -> user acceptance (done)
```

## 既定チーム

| 役割 | 責任 |
| --- | --- |
| `advisor` | 方向性、フレーミング、中心的な主張、証拠の十分性、論文戦略について独立に評価する。既定で建設的：まず成り立つ点を示し、結果を脅かす少数の問題を挙げ、それぞれに最小の修正または具体的な代替案を添え、最後に proceed / revise / stop を示す。助言のみで、ゲートではない |
| `researcher` | 文献検索、入手、精読、証拠の抽出、および主張 → 出典 → 位置の証拠表。共有 Zotero ライブラリを優先して検索し、必要な文献が見つからない場合は PDF 付きの正式版全文をインポートし、DOI とタイトルで重複を排除して、`zotero://` 参照をチームと共有します |
| `data` | 外部データセットとモデル重みの取得。出所の入手可能性とライセンス／アクセス状況の追跡、再開とレート制限に対応した取得ツール、公開元ハッシュによる完全性検証、展開、manifest 契約、検証済みの小さなサンプル、ディスク台帳を担当します。訓練コードの作成や評価プロトコルの変更は行いません |
| `designer` | 実験設計ドキュメントの所有者。問いと仮説、プロトコルと対照、ベースライン、アブレーション、メトリクスと統計計画、計算予算、および実行中の設計変更管理を担当します。実運用のコード作成や実験の実行は行いません |
| `builder` | コード、設定、データパイプライン、テスト、再現可能なエントリーポイント。長時間の訓練実行は行いません |
| `runner` | 訓練／評価の開始と監視。実行 ID、設定、シード、メトリクス、ログ、チェックポイント、成果物のパスを記録 |
| `reviewer` | 文献ノート、コード、結果、論文の主張／引用の独立した検証。ブロッキングとなる証拠を伴う PASS/FAIL |
| `writer` | LaTeX 論文ドラフト：本文、節、表、キャプション、引用、図のコード。実験の実行やコード／モデルの変更は行いません |

Lead は、目標の明確化、分解、ボード管理、割り当て、統合、要約、最終成果物の組み立て、納品を担います。メンバーは範囲を限定したサブタスクのためにサブエージェントを 1 層だけ使えますが、チームメイトを作成することはできません。 Lead は自身のツール呼び出しを抑え、短い進捗報告で足りることに追加のツール実行を重ねず、深い作業は担当メンバーに任せます。

### 共有 Zotero ライブラリ

researcher は、ユーザーの Zotero ライブラリをチームの共有文献ソースとして扱います。公開 Web を検索する前に、既存のコレクションとアイテムを検索し、添付済みの PDF と注釈の該当箇所を再利用します。不足している論文は、正式版（version of record）のみを PDF 付きでインポートし、プロジェクトのコレクションに整理します。インポートは DOI とタイトルで重複を排除し、ユーザーのタグとコレクションには手を加えず、`zotero://` のアイテム参照を証拠表とボードカードに記録します。これにより、すべてのチームメイトが同じ論文を読み、reviewer は同じページを抜き打ちで確認できます。全文がペイウォールの内側にある場合やメタデータしかない場合、researcher はリンクを記録し、代替品をインポートするのではなく、証拠をメタデータのみとしてマークします。

### アドバイザリー・レビュー

アドバイザーはゲートキーパーではなく、科学的な共同思考者である。まず計画のどこが成り立ち、なぜ成り立つのかを示し、次に結果を脅かす順に最大三つの問題を挙げ、それぞれを具体的なステップ、主張、数値に紐づける。各問題には、計画を受け入れ可能にする最小の修正、またはトレードオフを添えた具体的な代替案を必ず付ける。単なる却下はレビューにならない。「この計画では問いに答えられない」と「この計画は動くが弱い、または高コスト」を区別し、どの条件で計画が受け入れ可能になるかを述べ、最後に proceed、revise（必要な変更を列挙）、stop（代わりに取るべき方向を示す）のいずれかで締める。プロジェクトが実際に掲げた基準で判断し、その基準を明示する。最も厳しい基準を仮定しない。掲げた目標に対して妥当な計画は、より強い主張には追加の証拠が要るという理由で失敗とみなされない。目標そのものが誤っている場合は、範囲の決定として別途あなたに返す。判断に必要な証拠が欠けている場合は、決着をつけられる最も安価な実験または情報源を示す。妥当な計画には疑念を演出せず明確に支持を与え、stop には必ず代替方向を添える。あくまで助言であり、決定は Lead が行い、reviewer が独立した PASS/FAIL のゲートであり続ける。

相談は毎回 Lead が準備し、会話をそのまま転送しない。Lead はユーザーの問いを、advisor が答えるべき決定に翻訳する。争点となる主張や計画、現在の証拠とその範囲、机上の選択肢、制約、そしてユーザーがその回答から何を必要としているかを添える。曖昧または過載した問いはまず絞り込み、ユーザーの原文やチーム内部の経緯はそのまま渡さない。相談は決定点ごとに一度だけで、Lead が証拠から自分で弁護できる結論の確認や、Lead 自身の作業の要約には使わない。回答は転送文ではなく、科学的結論として、それが何を変え、どの決定をユーザーに残すかという形でユーザーに届ける。

## 設計のオーナーシップ

Lead は実験設計を書きません。設計が中心となる作業では、designer がプロジェクトワークスペース内の設計ドキュメント（`docs/design/<name>.md` またはプロジェクト既存の設計場所）を所有します。内容は、問いと仮説、プロトコルと対照、ベースライン、アブレーション、メトリクスと統計計画、計算予算、および実行中に行われた設計変更の変更ログです。

builder がその設計を実装し、runner がそれを実行し、reviewer は提案ゲートでその設計が問いに答えられるかを、結果ゲートで実行が設計と一致したかを確認します。advisor は提案ゲートで独立した科学的見解を示します。Lead は設計ドキュメントが存在し、researcher と data の入力が揃っていることを確認してから、そのステップを承認または差し戻します。実装主導の作業では、builder が設計を起草し、advisor が一度レビューします。

## 書き込み範囲

各ロールは自分の書き込み範囲の中だけに書く。advisor と reviewer は何も書かない。researcher は `literature/`、`notes/`、`docs/evidence` を、data は `data/`、`manifests/`、`scripts/` 配下のダウンロードスクリプトと `reports/` を、designer は `docs/design/` を、builder は `src/`、`configs/`、`tests/` を、runner は `runs/`、`logs/`、`checkpoints/` を、writer は `paper/`、`figures/` を持つ。Lead は制限なし。読み取り、検索、カードへのコメントは全員に開かれている。

範囲は嗜好ではなく契約である。他ロールに属する変更は、誤ったメンバーが書くのではなく、その所有者に報告する。advisor と reviewer は読み取り専用で起動するため、レビューは何を変えるべきかを報告し、自分では変えない。範囲外への書き込みが本当に必要なチームメイトは、作業開始前に Lead の明示的な例外を得て、カードに記録する。 他のすべてのロールは Lead の sandbox 権限を継承するため、そのロールが要求しない限り、チームメイトが Lead より強く制限されることはない。

カードを in_review に移す前に、所有者または Lead がロールと変更パス（または base と head のコミット）を指定して `research_scope_check` を実行する。違反は、変更を所有ロールへ移すか、Lead が承認した例外を記録することで解消し、カード進行中に範囲を広げない。プロジェクトは `AGENTS.md` やカードで範囲を狭めたり広げたりでき、そのステップではカードが優先され、後のセッションも同じ規則を読む。

## 実験の着手条件

計算資源は意思決定のために使い、作業量のために使わない。簡単なスモークテストを超える実行は、判定ルールを書き残すまで開始しない。ルールは「中止」を返せなければならない。着手前に、その実行が決着させる問い、仮説、支持と見なす効果量を含む期待結果、それを反証する結果、中止基準、上回るべきベースライン、決着させられる最小のパイロット、計算予算を設計文書かワークログに記録する。この記録のない実行は着手できない。

まずパイロットを回す。仮説をまだ反証し得る最小構成（1 シード、1 分割、部分集合、短い学習時間）で実行し、事前登録した閾値と照らして読み、拡大するかどうかを明示的に決める。パイロットが閾値に届かなければ、そのラインを停止し、負の結果を記録して報告する。差を平均で消すためにシードや変種を追加してはならない。変数は一度に一つだけ変え、実行前に交絡を明示し、実行途中のプロトコル変更は理由とともに記録する。実行は予算、同一失敗の 2 回目、指標が動かなくなること、の三つでも打ち切る。

Lead が実行を承認し、runner は記録がなければ起動を拒否し、reviewer は結果ゲートで実行が事前登録ルールに一致したか、停止決定が覆されずに守られたかを確認する。

## セッションの継続性

セッションは会話であり、プロジェクトそのものではない。作業を運ぶのはワークログ、ボード、git であり、チャット、チーム、バックグラウンドジョブはセッションとともに消える。`worklog/PLAN.md` が既にあるプロジェクトでは、最初の実質的な作業の前に PLAN と INDEX、続いて対象カードの現在状態ブロックを読み、それから計画を立てるか計算資源を使う。

ワークログは `research_project` が返すプロジェクトルートに置き、セッションのサブディレクトリには置かない。プロジェクト上の全セッションが一つの PLAN と INDEX を共有する。PLAN、INDEX、カードファイル、ボード、git、メモリは永続的だが、`team_task_*` の項目、チームメイトとの会話、バックグラウンドジョブはそのセッションにしか存在しない。後のセッションが知る必要のあることは、セッション終了前に PLAN かカードファイルへ書く。

ターンを超えて続く実行や長時間ジョブは、ジョブやターミナルのハンドル、ホスト、開始時刻、完了見込み、それが支える決定規則をカードファイルか PLAN に残す。再開時はまず生存を確認し、ハンドルが消えていれば孤児として扱い、成果物を突き合わせたうえで採用・再起動・停止をユーザーに諮る。同じ作業を黙って二度走らせない。既に存在しないセッションが保持するカードは、引き継がずユーザーに再オープンを求める。

## リサーチサイドバー

このプリセットは右サイドバーに「研究」タブを追加します。チームが今何をしているか、どこで詰まっているか、次の一歩は何かを示します: `worklog/PLAN.md` の目標とマイルストーン、`worklog/INDEX.md` のアクティブな作業項目（タスクボードは別で、ここには表示されません）、最近の実行、設計ドキュメント、アーキテクチャカードです。

アーキテクチャカードは `.research/architecture/` に JSON で保存されるノードとエッジの図で、1 枚につき 1 ファイルです。エージェントは `research_architecture` ツールで読み書きするため、図はスライドの中ではなく設計と同期したままになります。カードはパネル内で SVG として描画され、ノードの上をドラッグして範囲選択でき、書いたメモはカードの注釈として保存され、エージェントは回答前にそれを読みます。`dsh-better-sidebar` がインストールされていればそれ経由で、なければネイティブの右サイドバーに登録されます。

パネルは `panel/` 配下の独立したモジュールで、設定ページとは別に単独で有効化・無効化できます。各会話の右サイドバーのタブとして表示されます。

方法カードはデザイナー、実装カードはビルダーが所有し、アドバイザーは設計・実装の判断をレビューする前に両方を読み、レビュアーは結果ゲートで両方を照合します。中ボタンのドラッグでキャンバスを移動し、ホイールで拡大し、ノード上をドラッグして範囲選択して注記できます。

## タスクボードのワークフロー

```text
User goal
Lead:  research_project -> taskboard_create only at user gates (checklist, presetId=research-team)
       -> team_task_create (owner, blocked_by, write scopes) -> send_message
Member: team_task_update (claim) -> work -> team_task_update (complete) + send_message
Internal steps and member handoffs stay off the board; only user gates get cards
At a user gate: taskboard_get -> taskboard_move in_progress -> checklist/report -> in_review
Reviewer: independent PASS/FAIL with evidence on gated cards
Advisor: optional independent recommendation at key decisions or final review
Lead:  summarize -> report card ids/status/evidence/risks to the user
User:  accept in the GUI -> done (agents can never move a card to done)
```

ユーザーの確認や受け入れが必要なステップだけがボードのカードになります。成果物のチェックポイント、ユーザーが承認すべきスコープ判断、リスクの高い変更、最終引き渡しが対象です。内部ステップ、自己承認したサブタスク、メンバー間の引き継ぎは `team_task_*` で追跡し、ボードには載せません。ゲートに達したら、成果物・証拠・レビュー判定はカードに残します。チームメンバー間のやり取りは英語で行い、ユーザー向けの返信、カード、成果物はユーザーの言語に合わせます。 ユーザーの判断や不足情報が必要なときは、Lead が `ask_user_question` で直接尋ね、カードに待機状態を残しません。回答がタイムアウトしたら、Lead はアドバイザーに独立した助言を求め、記録してから作業を進めます。

## Git ワークフロー

このモードは実質的な作業の開始時に耐久記録を初期化し、その要求が本当の作業か単純な質問かはエージェントが判断します。ワークスペースがまだリポジトリ内にない場合、エージェントは `research_workspace_init` を呼び、`worklog/PLAN.md` と `worklog/INDEX.md` を作成して `git init` を実行します。ネストしたリポジトリは作成せず、足場をコミットすることもありません。

破壊的またはリスクの高い変更は、既定ブランチを直接編集せず、ステップ名のブランチ（例 `task/<title>+<id>`。ゲート対象の作業はカード、内部作業はチームタスク）で行います。カードまたはチームタスクには base と head のコミットを記録し、reviewer は `git diff <base>..<head>` をコードレビューの根拠とし、受け入れチェックも再実行します。

ブランチはカードが受け入れられた後にのみマージし、その後削除します。データセット、チェックポイント、ログ、キャッシュなどの生成物はリポジトリに入れません。git リポジトリでない場合は、ファイルハッシュのスナップショットとカードの証拠でレビューします。

## ワークログ

セッションをまたぐ可能性のある作業は、コードの隣に小さく有界な記録を残します。`worklog/PLAN.md` には目的、現在のマイルストーン、アクティブなカード、ブロッカー、日付付きの決定を、`worklog/INDEX.md` にはアクティブなカード 1 件につき 1 行を置きます。各カードには `worklog/<task-id>.md` があり、先頭に現在の状態ブロック、その下に短い追記エントリを置きます。

再開時、エージェントはまず PLAN と INDEX を読み、次に対象カードの状態ブロックと末尾だけを読みます。ファイル全体やディレクトリ全体は読みません。PLAN は約 100 行、カードファイルは約 200 行に保ち、完了したカードは索引から外します。3 種類のファイルの簡潔なテンプレートはプリセットの persona にあり、どのセッションもこのリポジトリを読まずに作成・更新できます。

## チームモデルプロファイル

設定ページは既定のチームメンバー用に複数の名前付きモデルプロファイルを保持し、次回の spawn には選択中のものを使用します。

次の場所を開きます:

```text
Plugins → dsh-research-team-preset → research-team-settings → Configure
```

ページ上部のプロファイルバー:

- **切り替え**: 次回の既定チームメイトが使うプロファイル（`团队配置` ドロップダウン）を選択します。
- **新建配置**: 8 つの空の役割行を持つプロファイルを追加します。
- **配置名称**: 選択中のプロファイルの名前を変更します。名前は必須で一意、60 文字以内です。
- **删除配置**: 2 回目の確認クリックで選択中のプロファイルを削除します。最後の 1 つは削除できません。

各プロファイルは既定メンバーごとに 1 行を持ちます:

- **モデル**: すべての provider のモデルを含む 1 つのドロップダウン。provider のグループヘッダーはクリックできません。モデルを選ぶと provider と model の両方が設定されます。
- **推論強度**: 選択中のモデルが公開している強度に、モデルの既定値オプションを加えた 2 つ目のドロップダウン。

モデルが空の場合は「Lead のルートを継承」、強度が空の場合は「モデルの既定値を使用」を意味します。`spawn_teammate_with_model` は `model` が省略されたときに選択中プロファイルの役割ごとの既定値を読み、明示的な `model` はそれを上書きします。通常の `spawn_teammate` は常に Lead を継承します。

推奨される能力ティア（あくまで出発点であり、規則ではありません）:

| 役割 | 推奨ティア | 理由 |
| --- | --- | --- |
| `designer` | 最強 | 設計の誤りはすべての実行を無効にする |
| `advisor` | 最強、designer とは異なるモデル系列 | 独立した批評には別の視点が必要 |
| `builder` | 高 | コードの正しさと長いコンテキスト |
| `reviewer` | 高、builder と runner とは異なるモデル系列 | 証拠監査には独自の視点が必要 |
| `researcher` | 中高 | ベースラインと SOTA の判断 |
| `writer` | 中 | 検証済みの証拠に基づく整理された執筆 |
| `data` | 中低 | ツールによる手順的な取得 |
| `runner` | 中低 | 深い推論よりもツールの信頼性 |

プロファイル一覧はまとめて保存されるため、プロファイルを切り替えても別のプロファイルでの編集は失われません。ページは保存前に名前を検証し、保存が拒否された場合はサーバーのエラーテキストを表示します。

行の名前が重要です: `research-team-settings` は**パッケージルート** `dsh-research-team-preset` に置く必要があります。DSH のクライアントモジュールスキャナーは、パッケージルートに完全一致する行についてのみ `dsh.client` を検出します。サブパスの名前ではホストプラグインは起動しますが、ページは決して読み込まれません。

### 設定の保存場所

```text
$DSH_HOME/research-team-settings.json
```

```json
{
  "version": 2,
  "activeProfileId": "default",
  "profiles": [
    {
      "id": "default",
      "name": "默认配置",
      "roles": {
        "advisor": { "provider": "example-provider", "model": "example-model", "reasoningEffort": "high" },
        "designer": { "provider": "", "model": "", "reasoningEffort": "" },
        "researcher": { "provider": "", "model": "", "reasoningEffort": "" }
      }
    },
    {
      "id": "p-example",
      "name": "快速实验",
      "roles": {
        "advisor": { "provider": "", "model": "", "reasoningEffort": "" }
      }
    }
  ]
}
```

- `activeProfileId` は次のチームメイトが使うプロファイルを指定します。値がない、または不明な場合は、サーバーが最初のプロファイルにフォールバックします。
- 旧形式のファイル（`{ "roles": { ... } }` または素の役割マップ）はメモリ内で `默认配置` という単一のプロファイルに移行されます。ファイルは次回の保存時にプロファイル形式で書き換えられます。旧形式の `POST { "roles": ... }` はアクティブなプロファイルだけを更新するため、古いスクリプトが他のプロファイルを失わせることはありません。
- JSON ファイルが信頼できる唯一の情報源です。ホストプラグインは起動時にこれを読み込み、`getSettings()` と `modelForRole()` はそこから更新されるため、ページと次のチームメイトは最新の値を参照します。
- ファイルが存在しない、または一時的に読めない場合は、消去せずに最後に正常だったメモリ内スナップショットを保持します。
- 設定ファイルはこのリポジトリには**ありません**。別途バックアップしてください。プロファイルごとではなく `DSH_HOME` ごとに存在します。
- 資格情報は保存されません。保存されるのはプロファイル名と provider/model/effort の文字列だけです。
- 設定の保存は DSH の再起動なしで反映されます。設定ストアはファイルを読み直し、次回の spawn がアクティブなプロファイルを解決します。このプラグイン自体のコードを変更した場合は DSH の再起動が必要です。ホスト側はホストレベルで WebSocket/HTTP ルートと Plugins ページのスロットを登録するためです。
- バージョン 0.1.0 は以前のビルドにおけるローダーのバグを修正します。ファイルは役割を `"roles"` の下に包みますが、古いローダーはオブジェクト全体を役割ノーマライザーに渡していたため、再起動後にすべて空の設定が生成されていました。現在のローダーは `"roles"` を展開し、旧ファイルを移行し、互換性のために素の役割マップもサポートします。

| プリセット ID | `cordis.patch.yml` | `research-team`。タスクカードでは `presetId=research-team` を使う |
| ペルソナ | `cordis.patch.yml` | 英語のシステムプロンプト。モード全体のルール |

## 仕組み

- **プリセット**: `cordis.patch.yml` がペルソナ、ツール行、modeled-teammates サブモジュール、トップレベルの設定行を宣言します。
- **タスクボードのプロンプト**: `plugin/index.js` がプリセットスコープに英語のプロトコル節（`plugin:dsh-taskboard`）を登録し、現在のワークスペースを解決する `research_project` を提供します。
- **役割ごとのルーティング**: `plugin/modeled-teammates.js` が `subagents.startActivation` を `AsyncLocalStorage` でラップし、`spawn_teammate_with_model` の呼び出しに限って `agentOptions` を注入します。公式の Agent Teams パッケージには手を加えません。 Cordis はサービスをトレース可能なプロキシとして返すため、ラッパーはメソッドの同一性ではなく自身のプロパティ記述子を検証します。
- **設定**: `settings/index.js` がプロファイルの JSON ファイルを読み書きし、`GET/POST /api/dsh-research-team-settings` を提供します。`client/index.js` は `plugins.row.config` を通じて Plugins ページのプロファイルエディターを登録します。
- **更新**: `plugin/settings-store.js` がメモリ内スナップショットを保持し、読み取りと spawn のたびにアクティブなプロファイルを解決します。読み取りに失敗した場合は最後に正常だったスナップショットを保持します。

## トラブルシューティング

### 再起動後に設定がリセットされたように見える

バージョン 0.1.0 は既知の原因を修正します。古いローダーは `{ roles: ... }` オブジェクト全体を役割ノーマライザーに渡し、すべて空の設定を生成していました。0.1.0 以降に更新して DSH を再起動し、次を確認してください:

- `$DSH_HOME/research-team-settings.json` が存在し、保存したプロファイルが含まれているか。
- 古い `{ "roles": ... }` ファイルは単一の `默认配置` プロファイルとして表示され、次回の保存時にプロファイル形式へ書き換えられるか。
- `research-team-settings` 行の名前が正確に `dsh-research-team-preset` か。
- 現在のホストがこのチェックアウトを実行しており、古いインストール済みコピーではないか。

### 各チームメイトは Lead のモデルで実行される

メンバーの最初のメッセージの上に出力される spawn の結果を確認する。設定済みまたは明示的なルートが適用された場合は `requested=<provider>/<model> effort=<effort>` と表示され、どのルートにも一致しなかった場合は `requested=inherit (Lead route)` と `note:` 行が表示される。`note:` が役割名を示している場合は、その役割にアクティブなプロファイルで provider/model が設定されていない。名前が標準の役割ではないという注記は、チームメイト名に役割の語が含まれていなかったことを意味する。

ほかに設定ファイルとは無関係な原因が二つある。

- Lead が modeled ツールではなく通常の `spawn_teammate` を呼んだ場合。これは常に Lead を継承する。persona は Lead に、modeled ツールへ `model` を渡さず、名前が不確かだからといってフォールバックしないよう求めている。

- 設定行が、実行中のホストが読むのとは別の `DSH_HOME` の下に保存されている場合。`research_team_routes` が出力する `settings file:` 行と `echo $DSH_HOME` を比較する。

### 設定ページが Plugins に表示されない

- 行はパッケージルートである必要があり、`dsh-research-team-preset/settings` ではいけません。
- クライアント側はインストール後に DSH の再起動とブラウザのリロードが必要です。
- バンドルがプロファイルで有効になっているか確認してください。

### チームツールが見つからない

同じプロファイルで [`@deepseek-ai/dsh-experimental-agent-team-profile`](https://github.com/deepseek-ai/deepseek-harness) を有効化し、再起動してください。インストーラーはこれを促しません。

### タスクボードのツールが見つからない

同じプロファイルで [`dsh-taskboard`](https://github.com/cloader/dsh-taskboard) を有効化し、再起動してください。

### `spawn_teammate_with_model` が利用できない

このサブモジュールは内部のサブエージェントサービスをラップしています。DSH のアップグレードでアクティベーションの形が変わる可能性があります。失敗メッセージを確認し、ラッパーをインストールできない場合は `research-modeled-teammates.enabled: false` を設定して再起動し、通常の `spawn_teammate` を使用してください。

### プリセットが一覧にない

バンドルがインストールされ有効になっていることを確認し、DSH を再起動して新しいセッションを開いてください。プリセットの宣言は起動時に読み込まれます。

### `research_project` がワークスペースを解決できない

作業ディレクトリを GUI で DSH プロジェクト／ワークスペースとして開くか、既知のプロジェクトを渡してください。ツールは推測しません。

## 既知の制限

- 役割ごとのモデルルーティングは内部サービスラッパーであり、公式の Agent Teams 拡張ではありません。DSH のアップグレードで壊れる可能性があり、フォールバックは上記に記載しています。
- プロファイルレベルの依存関係は自動ではインストールも有効化もされません。このリポジトリはそれらを文書化しますが、管理はしません。
- チームモデルプロファイルは `$DSH_HOME` 配下の独立した JSON ファイルにあり、DSH 標準の設定エクスポート／バックアップには含まれません。マシンを移行する場合はファイルをコピーしてください。
- モデルメニューは provider グループ付きのネイティブ `<select>` であり、検索可能なカスタムピッカーではありません。
- このモードはセッション開始時に 8 名のチームメイトを自動生成しません。Lead がタスクの必要に応じて役割を作成します。
- このモードは既存リポジトリの中にリポジトリを初期化せず、ワークログやリポジトリの足場を自動でコミットすることもありません。
- メンバーはサブエージェントを 1 層まで使えます。より深い委任は意図的に無効化されています。
