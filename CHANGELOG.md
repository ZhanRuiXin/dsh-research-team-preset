# Changelog

All notable changes to Research Team Mode are documented here. The project uses semantic versioning. The plugin is published on npm as `dsh-research-team-preset`; the current release is 0.1.1.

## Unreleased

- Work items now follow a fixed status table (`todo -> in_progress -> in_review -> done`, with `blocked` and `canceled` as side states): `blocked` requires a reason, a gate requires at least one evidence entry or a noted checklist item, every move is kept in the item history, and the translated READMEs were updated to the JSON worklog.

- The Research panel now opens with the live team roster, laid out as a compact two-column grid instead of one full row per member: the avatar shows the member's initial, a pulsing dot marks a running member, and each tile carries the name, a Lead accent, and a status pill (运行中 / 空闲 / 启动中 / 失败); hovering a tile opens a small card with what that member is doing — its current work item, that item's status and next step, when it was last updated, and the model — and the section header counts running members.

- The Research panel copy reads formally: the header names the team, each empty state says what is missing and which tool writes the record, and the annotation, approval and refresh messages are complete sentences instead of shorthand.

- The worklog is now a JSON store under `.research/worklog/` (`plan.json` and one `items/<id>.json` per item) with generated markdown views, and new tools own it: `research_worklog` (init, list, get, update, claim, gate, plan), `research_state`, `research_decision`, `research_evidence` and `research_design`. `research_workspace_init` imports a legacy markdown plan and index once, then regenerates the views.

- Experiments follow an explicit lifecycle (planned, awaiting approval, approved, running, completed, stopped, failed, rejected) driven by the new `research_experiment` tool (register, start, finish) instead of hand-edited manifests. The section also gained an approval switch (requires approval / auto), per-run approve and reject buttons that write into the run's manifest, elapsed or total run time, newest-first ordering, completed runs, and an internal scrollbar when the list grows.

- The team records everything in its own worklog: `worklog/PLAN.md`, `worklog/INDEX.md` and one card file per gated item are the only ledger, the injected worklog protocol and and the persona coordination section were rewritten for it; the optional integrations list now names only Zotero and Mnemon, and the `presetId` wiring was removed from the README and the eleven translations.

- The sidebar list is now called work items and says it reads `worklog/INDEX.md`; task-board cards are documented as separate and are no longer implied to appear there.

- The run manifest and the design `## Question` heading are now part of the admission and review gates, so the sidebar record is required rather than merely described.

- The persona now states what the Research panel reads, so the team writes the run manifest and the worklog rows instead of assuming the panel fills itself.

- Architecture cards centre the boxes that share a column, so a vertical flow reads as one centred column instead of a left-aligned staircase.

- Architecture node boxes size themselves from their labels: one line if it fits, two if it must wrap, so a card no longer leaves an empty half or clips a word.

- Architecture labels wrap on the measured text width instead of a character count, so a mixed Latin/CJK label no longer leaves one stray character on the second line.

- Research sidebar: a Research entry in the left rail and a right-side tab show the objective, active cards, runs, design documents and architecture cards, registering through `dsh-better-sidebar` when present and the native sidebar otherwise; architecture cards live in `.research/architecture/`, render as SVG, support box-selection annotations, and are edited by the agent through the new `research_architecture` tool. The panel ships as its own module under `panel/`, independent of the settings form.
- Architecture cards are owned by the role that realizes them (designer: method, builder: implementation), the advisor reads them before a review and the reviewer checks them at the results gate; the canvas pans with the middle mouse button and no longer selects text while dragging a selection box.
- The panel is registered only in the session sidebar (the better-sidebar tab when that plugin is present, otherwise the native right-pane tab); it no longer adds a left-rail entry or a main-panel view.
- The Research tab waits for the better-sidebar service instead of probing once, so after a restart it loads without toggling the module off and on.
- Canvas fixes: node labels wrap by measured glyph width and are clipped to their box, a left click on a card node toggles its selection instead of starting a marquee, a left click on empty space clears the selection, and cards are drawn left to right on a 520x300 canvas.
- The Research panel got a visual pass: a token-based stylesheet with light and dark support, a fitted architecture view that fills the column, landscape architecture cards laid out left to right, seed progress on runs, and a compose card for annotations.

- Answers obey the ask: the Lead keeps the user's questions as the contract for the turn, delivers the requested survey, extension list, or decision before any research program, walks each question in the reply, and says plainly when one cannot be answered yet.
- Long turns are not silent: after about ten minutes of tool work without a user-visible answer, the Lead sends a short interim answer (what is settled, what is still being gathered, when the next answer comes) so the user can redirect before the compute is spent.
- Negative prior results constrain the method, data, and budget that produced them, not the idea itself. Before a direction is closed it is steelmanned and shown to fail, and every "cannot be claimed" is paired with the version that could be claimed and the evidence that would earn it.

## 0.1.1 — 2026-11-10

- The settings row survives a re-apply of the bundle inside one process: when the host re-mounts the plugin after a profile or hot reload, it reuses the live `/api/dsh-research-team-settings` handler instead of failing with `webserver: duplicate exact route`. Added `test/settings-route.test.js` and removed the stale `@local/dsh-research-team-preset` link and lockfile entry from the profile.

## 0.1.0 — 2026-11-10

First public release.

- Published on npm as `dsh-research-team-preset`; the README installs from npm, from a pinned git tag, or through the DSH plugins page (Settings → Plugins → Add).
- Task board, Zotero, and Mnemon are documented as optional integrations: the preset runs without them and links to them only when they are installed.
- The README is now a public overview: contributor material (repository layout, verification checklist, development loop, versioning) moved to `DEVELOPMENT.md`, and all eleven translated READMEs follow the same structure.

- Eight standard roles: advisor, designer, researcher, data, builder, runner, reviewer, writer.
- `designer` owns the experiment design document (questions and hypotheses, protocol and controls, baselines, ablations, metrics and statistical plan, compute budget, design change log); the builder implements it, the runner executes it, the reviewer checks adherence, and the advisor reviews the design at the proposal gate; the Lead gates the step but does not author the design.
- Advisory review is constructive by default: the advisor states what holds before what does not, ties each objection to a specific step or number, attaches the smallest repair or a concrete alternative, separates "cannot answer the question" from "weaker or costlier", and never recommends stop without a replacement direction. The persona gains an `## Advisory review` section, the README gains a matching subsection, and the Lead now attaches the plan or claim plus the decision it needs to a consultation.
- Advisory review is calibrated to the bar the project actually committed to: the advisor names that standard (taken from AGENTS.md, the card, or the user) instead of assuming the most demanding one, treats a plan that is sound for its stated target as sound even when a stronger claim would need more evidence, and raises a wrong target separately as a scope decision for the user.
- Lead communication is scientific: the persona and README now require replies to lead with the claim or result and the evidence behind it (run id, dataset, metric with uncertainty and sample size, source), to label each statement as observed fact, inference, hypothesis, or open question, and to say what would change the conclusion. Internal process (agent handoffs, retries, tool errors, board bookkeeping, what the team learned while working) is not forwarded unless it changes how a result reads or blocks a decision, and member reports are translated rather than pasted. The persona states the human–machine division of labor: the user sets direction and judges evidence, the team carries search, implementation, experiments, and verification.
- Consistency audit: the persona no longer asks the Lead to relay internal progress or ownership to the user. What reaches the user is the scientific issue, the evidence in flight, the scope a result holds under, and the decision needed; member reports are marked as internal input for the Lead. The eleven translated READMEs are brought back in line with the final-review wording of the advisor line.
- Docs parity: all eleven translated READMEs now match the English structure — the Lead-communication section, the advisory-review guidance, the updated advisor role row, and the troubleshooting subsection on teammates running on the Lead's model were missing and are now translated in each language.
- Experiment admission: the persona and README require a written decision rule before any run (question, hypothesis, expected outcome and effect size, the result that would refute it, kill criterion, baseline, cheapest pilot, budget), a pilot that must pass before scaling, a binding stop when it misses, one variable at a time, and a run bounded by budget, repeated failure, and a flat metric. The Lead admits the run, the runner refuses to launch without the record, and the reviewer checks that a stop decision was honored rather than overridden. This closes the blind-running failure mode where extra seeds and variants were added to average away a miss.
- Consultation preparation: the Lead turns the user's question into the decision the advisor must answer — claim or plan at issue, current evidence and its scope, options, constraints, and what the user needs from the answer — sharpens a vague or overloaded question first, does not forward the raw message or the team's internal history, asks once per decision point, and relays the answer as a scientific conclusion and the decision it leaves open. The advisor is expensive, so a consultation is prepared rather than forwarded.
- Cross-session continuity: the worklog lives at the registered project root rather than in a session subdirectory, and a session that finds an existing PLAN reads PLAN, INDEX, and the current card's state block before planning or spending compute. The persona separates durable state (worklog, cards, board, git, memory) from session-scoped scratch (`team_task_*`, teammate conversations, background jobs), requires an in-flight run to record its handle, host, start, expected completion, and decision rule so a resume can check liveness before duplicating spend, and reports a stale card claim to the user instead of taking it over.
- Write envelope: each role writes only inside its own scope — advisor and reviewer nothing, researcher `literature/`, `notes/`, `docs/evidence`; data `data/`, `manifests/`, `scripts/`, `reports/`; designer `docs/design/`; builder `src/`, `configs/`, `tests/`; runner `runs/`, `logs/`, `checkpoints/`; writer `paper/`, `figures/`; the Lead unrestricted. The advisor and reviewer spawn read-only (a `sandbox/mode` record on the child session, with a tool guard as fallback on hosts that ignore it), `spawn_teammate_with_model` gains a `permission` argument, and the new `research_scope_check` tool compares a role's changed files or a `git diff` against the envelope, so an out-of-scope handoff fails before the card reaches review.
- Lead-permission inheritance: the advisor and the reviewer still spawn read-only, but every other role now inherits the Lead's current sandbox mode — including `danger-full-access` — instead of being pinned to `workspace-write`. The `permission` argument accepts all three modes, the deployment default remains the fallback when the Lead's mode cannot be resolved, and the write envelope still bounds what a role may write regardless of how broad its sandbox permission is.
- Documentation cleanup: the README and the eleven translations no longer list Git Bash as a prerequisite (the preset already uses the platform's native shell tool) or the Web GUI as an external capability (it ships with DSH). The requirements table now names only DSH, Agent Teams, the task board, and the PTC runtime. Every README opens with the official "powered by dsh", DSH 0.2.x, and MIT badges, and closes on the badge-free acknowledgements.
- Role boundaries: the runner diagnoses failures but does not patch code, the reviewer focuses on design at the proposal gate and evidence/deviation at the results gate, and the writer works from a pre-checked evidence pack.
- Model guidance: designer and advisor strongest, builder and reviewer next, researcher mid-high, writer mid, data and runner cheapest reliable tool-using models; reasoning effort is set separately.
- `data` role for external dataset and model-weight acquisition: source availability and license/access tracking, download tooling with resume and rate-limit handling, integrity checks against publisher hashes, unpacking, the manifest contract, one small validated sample, and the disk ledger.
- Data handoff: the manifest plus a validated sample unblocks format-adaptation code, so builder work depends on the sample step rather than the full transfer, and a long download never stalls the builder.
- Git workflow: when the request is substantive work rather than a simple question, the agent initializes durable tracking itself with `research_workspace_init`; the tool creates the worklog scaffold and initializes a repository only when the workspace is not already inside one, never nested and never committing. Destructive or risky changes run on a step-named branch; the reviewer reads the card's diff range; a branch is merged only after acceptance; generated artifacts stay out of the repository.
- Worklog discipline: `research_workspace_init` seeds `worklog/PLAN.md` and `worklog/INDEX.md`; work spanning sessions keeps them Lead-maintained plus one bounded `worklog/<task-id>.md` per gated card, with a current-state block at the top and short append-only entries. Resume reads PLAN and INDEX first, then only the target card's state block and tail. Compact templates for all three live in the persona so every session sees them without reading the repository.
- Gate-based task-board workflow with a Lead bridge, per-gated-step ownership, execution reports, and a human-only `done` gate; internal assignments, ordering, and handoffs run on `team_task_*`.
- Task board scope: cards mark the steps that need the user's review or acceptance (deliverable checkpoints, scope decisions, risky changes, final handoff), while internal assignments, self-approved subtasks, and member-to-member handoffs are tracked with `team_task_*` and stay off the board. The persona and the injected board protocol state the split.
- Prompt audit: the persona, the injected board protocol, and the README now tell the same two-ledger story across the roster, dispatch, worklog, git, and communication sections; a gated step's owner claims its card before starting, and a card may sit in todo while internal work runs.
- Team communication: internal messages between the Lead and teammates, spawn prompts, shared team tasks, and handoff notes are written in English; user-facing replies, board cards, execution reports, and deliverables follow the user's language.
- User questions: the Lead asks with `ask_user_question` instead of setting `waitingForHuman`/`waitingReason` on cards; a question that stays unanswered past the wait timeout becomes an advisor consultation, recorded before the work continues.
- Lead focus: the Lead keeps its own tool use light, skips ritual checks when nothing changed, batches related operations, and prefers a short user-facing update over another routine call; deep work belongs to the owning member.
- Shared Zotero literature: the researcher searches the user's Zotero library before the open web, imports a missing paper's formal version of record with its PDF (deduped by DOI/title, filed in a project collection), and shares `zotero://` item refs on the evidence table and the gated card. Paywalled or metadata-only evidence is labelled instead of substituted.
- Opt-in `spawn_teammate_with_model` submodule for per-role provider, model, and reasoning effort.
- Multiple named team model profiles: create, rename, switch, and delete profiles from the Plugins page, with eight role rows each, a provider-grouped model menu, and a separate reasoning-effort menu. The selected profile supplies the next teammate's route.
- Settings page role order follows importance and task flow: advisor, designer, researcher, data, builder, runner, reviewer, writer, so the roles that carry the strongest models and the earliest decisions are configured first.
- Profile settings persisted to `$DSH_HOME/research-team-settings.json` as `{ version: 2, activeProfileId, profiles }`, refreshed from disk on reads and teammate spawns. Legacy `{ roles: ... }` files migrate to a single `默认配置` profile.
- Settings API: `GET/POST /api/dsh-research-team-settings` reads and writes the whole profile list; a legacy `{ roles: ... }` POST updates only the active profile.
- Fixed `spawn_teammate_with_model` on current builds: Cordis wraps every Service instance in a traceable proxy whose method reads are re-wrapped on each access, so the old identity check reported "patch did not take effect" even after the wrapper was installed, and the tool stayed permanently unavailable. The patch now verifies the own property descriptor instead. The harness covers configured-role injection, explicit overrides, plain inheritance, and restore on dispose.
- Fixed the modeled spawn itself: `spawn_teammate_with_model` passed the prompt as a bare string, while the Team spawn path expects typed content blocks, so every modeled spawn failed with `content.some is not a function`. The tool now passes `[{ type: 'text', text }]`, matching the built-in `spawn_teammate`.
- Fixed teammates silently inheriting the Lead route after DSH reopened until the settings page was saved once. Route lookup no longer depends on the top-level settings row having filled the in-process store first: `plugin/settings-file.js` reads `research-team-settings.json` at spawn time (same path rule and same version-2/legacy tolerance as the host plugin) and the store is only a fallback. A file written with a UTF-8 byte-order mark no longer empties every role either.
- Made the inheritance visible instead of silent: the spawn result prints `requested=<provider>/<model>` with the matched `role` and route source, and carries `diagnostics` when a role has no configured route, when a name matches no standard role, or when the settings file is missing or unreadable. The submodule also logs the resolved route count and profile at startup, so a boot where nothing resolves says so.
- Teammate names resolve to a role by whole-word match (`ELHA-R advisor`, `advisor-hi`, `senior_reviewer`) instead of requiring the exact role name, which previously made a descriptive name spend no configured route.
- Added the read-only `research_team_routes` tool so the Lead can read the configured per-role table instead of guessing provider and model names, and the persona now states that omitting `model` on `spawn_teammate_with_model` is not the same as `spawn_teammate`, and that it must not fall back just because it is unsure.
- Added `test/modeled-teammates.test.js` (`node --test`): route resolution with an empty store, explicit overrides, inheritance diagnostics, legacy `{ roles }` files, a byte-order mark, a missing file, the role-name matcher, and the routes tool.
- English system prompt and English README; full translations in 11 additional languages under `docs/`.
- Fixed a settings loader bug from earlier builds: the file stores roles under `"roles"`, and the old loader passed the whole object to the role normalizer, producing all-empty settings after a restart.
